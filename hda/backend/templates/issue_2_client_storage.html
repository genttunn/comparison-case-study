What levi could still do — session riding

Even though document.cookie is empty, an XSS payload could still make credentialed fetch() calls from within alice's browser — the browser attaches the session cookie automatically on every request. Levi could read alice's private data or perform actions on her behalf while she is on the page.

However, levi cannot read the cookie value, cannot exfiltrate it, and cannot use it from another machine. The moment alice closes the browser or the session expires, levi retains nothing. This is session riding — a weaker, transient attack — not credential theft.

Note: This does not mean the HDA is safe from XSS. It means the attacker walks away with no portable credential. Compare with the SPA, where the stolen JWT works from any machine until it expires.

Why the HDA is structurally safer:

The HDA uses a server-side session. The browser holds only an opaque session ID in an HttpOnly cookie — JavaScript cannot read it. No sensitive credential ever lands in localStorage or anywhere JS can reach. This is the natural outcome of server-side session philosophy, not a deliberate hardening step.

The SPA could also use an HttpOnly cookie for its JWT — but someone has to make that explicit decision. The default SPA pattern puts the token in localStorage because it is simpler. The HDA has no such choice to make.
