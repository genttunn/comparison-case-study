What the server sees

  

    Tampering: Read localStorage and Tamper DOM value run entirely in the browser.
    Refresh the log after clicking either one. Nothing new appears, because neither action sent a request.
    This is a browser-level limit, not something either architecture fixes. No difference between SPA and HDA.
  

  

    Scraping: Scrape all pages fetches every page one by one, using normal routes.
    Refresh the log after clicking it. The entries look identical to a user clicking through pages by hand.
    Neither app checks for unusual request patterns. No difference between SPA and HDA.
  







  
Part 3: Where does the computation happen?

  

    Add a task using the form below. Both apps compute "days since creation" with the same formula.
    This app (HDA) computes it on the server. The server log will show both the task creation and
    a warning about the buggy computation result.
  

  

    

      
      
    

    
  

  






  
Where the bug lives

  

    HDA: the server fetches the task from the database and computes
    "days since creation" with an off-by-one bug: (now - created_at).days - 1.
    For a task created today, the result is -1.
  

  

    The server log recorded both the task creation and a bug_warning entry with the
    faulty value. To find this bug, you check one place: the server. Refresh the log panel above
    to see the warning.
  

  

    This is a debugging observation, not a security issue. It shows that when the HDA keeps all
    state logic on the server, bugs in derived values are logged and visible in one centralized place.
